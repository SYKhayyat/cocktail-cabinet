* Read this part even if you read nothing else

** The seven games never changed. Everything around them did.

The Cocktail Cabinet is a website with seven arcade games in it. There are still
exactly seven, they still play the way they always played, and the way they are
wired together has not changed since the beginning.

That is the surprising part, because the last time this document was written the
cabinet was 4,371 lines long and this one is longer. In the 113 commits since, not
one rule of play changed. What changed is that the *machine was taken apart to be
measured*, and then three drawers were added that have nothing to do with the seven
games.

The picture that carries the whole thing. The right-hand column names five words;
all five are in the glossary later, and each is defined by what its left-hand column
does:

| In the arcade cabinet | In this codebase |
|------------------------+-------------------|
| the rulebook inside a cartridge, readable on its own | the **model** — =src/games/<name>/model.js= |
| the cabinet body: screen, joystick, coin slot, power | the **engine** — =src/engine.js= |
| the wrapper that makes a cartridge fit the slot | the **facade** — =src/games/<name>/index.js= |
| the drawer labelled "Snake" | the button in =index.html= |
| *a workbench with the rulebook out of the cartridge* | the test suite, =tests/= |

Two more words you will meet early, defined by their jobs: the **controller** is the
part of a cartridge that turns key presses and mouse moves into something the rulebook
understands, and the **view** is the part that paints the rulebook's numbers onto the
screen. A cartridge is four files: model, facade, controller, view. A **mode** is one
of the settings in the "You control" dropdown — steer the snake, or place the apples.

The old version of this document could only read the rulebook with the machine
plugged in and switched on. The rulebook only existed while the machine was
running. That is now reversed. **You can pull the rules out, hold them, read them,
and run them on a bench with no screen and no power supply.** That is what all
11,685 lines of the test suite are, and it is why three new drawers became
possible.

**The three new drawers**

1. **A chat drawer.** =src/ai/= runs a real language model — a small one, on your
   own machine, with no account and no key. The chat game was always a stub. It
   now talks to a real brain, or to another browser, or to nothing, and it says so.
2. **A control panel for playing without sight.** =src/nonvisual.js= lets you read
   the board as words and press buttons instead of moving a mouse. Every one of the
   twenty modes works through it.
3. **A security cage.** =_headers= and =vendor/ai/= and two verification scripts
   add a set of rules about what the page is even allowed to load, plus a
   fingerprint check on the 21-megabyte model engine before it is allowed to run.

**What was actually wrong, and it is one thing wearing seventy hats**

Here is the belief that was held for most of this project's life:

> The words on the screen describe what the code underneath is doing.

It was not true, and it was not true in one place. It was false everywhere:

- The left-hand menu promised "You vs computer." For four games, in their default
  setting, there was no computer anywhere in the file. The computer code existed.
  It only ran if you picked a different option from the same menu.
- Every game's help text listed keys. Some of those keys did nothing in the mode
  the help text was describing.
- Splat's Builder mode said "Wheel to pan." The wheel did not pan. It scrolled the
  whole web page instead, and the code that should have caught it never ran.
- Snake's game-over screen told you to press "New round." The button says "New game."
- The Lives box offered a budget to Missile Command, which has no retry lives at
  all. It hid itself eventually.
- Splat's puzzle told you "You cleared the route!" — but the computer was the one
  navigating, and when the computer ran out of lives, which meant your route was
  *unsolvable*, the screen congratulated you.

**What that cost.** Not crashes. Not lost data. Nothing that a bug tracker would
call an outage. It cost a person being told a small lie by a machine while they
were playing it, about seventy separate times, in a project whose entire
front-page claim is honesty about what the machine is doing. Every one of those is
now a named issue, a named commit, and a test that fails if the lie comes back.

**And that is the actual fix, and it is not better wording.** The fix is that a
machine can no longer *claim* anything without the code producing it. The help text
is generated by the same function that reads the keys. The status line is computed
from the game's real state. The tie cannot be described as a win because a test
asserts that the words "highest score" never appear when the scores are equal.
Every game's rules can now be run for a thousand simulated games and asked
numerical questions about itself.

**The whole thing in one sentence**

The seven games are unchanged; what was built around them is a bench on which the
rules can be read and run without the machine, three new drawers built on that
bench, and a test suite that makes every claim the machine makes about itself into
something that can be proven wrong.

Everything below is that same idea in more detail.

Twelve words. The skill for this document says about ten. Twelve is what it takes

| word | what it actually is | why anyone cares |
|------+---------------------+------------------|
| model | =src/games/<name>/model.js=. The rules of one game and nothing else. No screen, no keyboard, no browser. It knows where the ball is; it does not know a mouse exists. | It can be run on its own. That is the whole reason the rest of this document exists. |

* The story

**What the cabinet does all day**

1. The page opens. =src/main.js= immediately builds all seven games and puts a
   button for each one down the left side.
2. Snake loads. The engine paints a dark rectangle with a box on it that says READY.
3. Nothing moves, because the cabinet is waiting to be told to start.
4. The human presses *New game*. A countdown runs for three seconds.
5. Then the loop starts doing real work, sixty times a second, until a life is lost.
6. The human clicks a different drawer. The same loop keeps ticking. Different cartridge.
7. Six of the seven are board games. The seventh, Imitation, has no board at all — it
   has a chat box, and it runs its own timer inside the same loop.

**How the seven are held together, in one function**

Here is the entire agreement. It is the loop that runs about sixty times a second.
It asks the loaded game three questions per tick — take one step, paint yourself, and
tell me your words for the player:

#+begin_src js
// src/engine.js:352-354, 359 — the three questions, asked sixty times a second

  this.game.update(delta, this.input);
  this.resolveUpdate();
}
this.game.draw(this.context);

That is the whole contract. Seven files, each written from scratch, each answering
those three questions by name. There is no shared parent class and no list of games
that the games themselves can see.

**Then the bug, told as a story**

In September 2026 somebody audited this project and wrote down 82 problems.
=issues.md= still holds that audit. Read the counts: 82 findings, and if you sort
them by *what kind of thing was wrong*, they collapse into one kind.

Roughly forty of them are the same defect. The rest are variations on it.

The belief was: **the words on screen describe the code underneath.** Every one of
those forty is a case where they did not, and in most cases the code was right and
the words were wrong. Not the reverse. That matters, because it means the fix is not
"make the code more careful," it is "stop the words from being able to drift."

Concretely, three real ones, quoted:

The help text for a mode came from a hand-written table that had drifted away from

**The cost, stated plainly**

A person playing this, being told something false about the machine they were
playing. Seventy times, across the twenty modes. No data was lost and nothing
crashed. The cost was entirely in trust, and it was small and repeated, which is
the kind that is easy not to notice and hard to unlearn.

**The fix, in one sentence, and its consequences**

The machine can no longer state anything the code has not computed, and the rules
can be run without the machine, so all of that is now checkable.

The consequences:

- The on-screen help is written by the code that reads the keys.
- The status line is computed from real state, every frame.
- The two modes that report life counts report them only if there are two pilots.
- The board can be read as text, and every mode can be played from that text.
- The model files can be run for a thousand simulated games and asked numerical
  questions about their own difficulty.
- 22 separate browser suites check that the live page behaves, not a stand-in.
- The 21-megabyte model engine has a fingerprint on it, checked before it runs.

**What "headless" buys, concretely, with a number**

Because the rules run without a browser, a computer opponent's difficulty can be a
number rather than an opinion. Splat hands a new player a route. There is a test
that plays that route 100 times and asserts the ball never dies on it:

#+end_quote

Make the gaps a little harder and the same 100 runs give you this, quoted from the
same file:

Nobody played that. That is 100 simulated games finishing in about a second, and it

** =src/geometry.js= — 18 lines. Four maths helpers and nothing else.**

This file exists because two different kinds of code need to agree about distance
and about "is this thing touching that thing", and they used to have two copies of
the arithmetic. It was split out of =src/engine.js= so that the game rules could
use it without importing the thing that owns the screen.

Four functions, complete:

#+begin_src js
// src/geometry.js:1-18 — the whole file
// Pure geometry shared by headless models and browser views.
export function clamp(value, minimum, maximum) {
  return Math.max(minimum, Math.min(maximum, value));
}

export function distance(ax, ay, bx, by) {
  return Math.hypot(ax - bx, ay - by);
}

export function circleHitsCircle(ax, ay, ar, bx, by, br) {
  return distance(ax, ay, bx, by) < ar + br;
}

export function circleHitsRect(circle, rectangle) {
  const closestX = clamp(circle.x, rectangle.x, rectangle.x + rectangle.width);
  const closestY = clamp(circle.y, rectangle.y, rectangle.y + rectangle.height);
  return distance(circle.x, circle.y, closestX, closestY) < circle.radius;
}
#+end_src

In English: =clamp= puts a number between a floor and a ceiling. =distance= is
straight-line distance between two points. =circleHitsCircle= asks whether two
round things overlap. =circleHitsRect= asks whether a round thing touches a
rectangle — it works by finding the nearest point *on* the rectangle and asking
whether that is closer than the circle's radius.

The last one is the interesting one. A naive version compares the circle's centre to
the rectangle's centre and is wrong whenever the circle is over a corner. This one
is right for corners, edges, and full overlap.

**What this buys:** the game rules and the drawing code now cannot disagree about
whether a collision happened, because there is only one arithmetic left.

** =src/decisions.js= — 10 lines. The sealed notebook the computers write their
reasoning into.**

Every computer opponent in this project explains each decision it makes — which
direction, which target, whether it was reacting or committed. Those explanations
used to be private fields on the model, which meant a test could not read them
without reaching inside the object it was trying to measure. This file is the
notebook, and it is shared.

**The apple placement, and why it is written the way it is.**

#+begin_src js
// src/games/snake/model.js:158-182 — placing an apple, with the reasoning intact
// Two passes and exactly one random draw per placement: count the free cells,
// pick an index, then walk to that cell. Neither pass allocates, so this
// avoids the ~2,600 object allocations the original array-building version
// performed per apple.
//
// The single draw is deliberate. Reservoir sampling also avoids allocation,
// but it consumes one Math.random call per free cell, which changes how many
// values the seeded Monte Carlo suite consumes per turn -- that silently
// resampled the opponent's mistake rolls and moved the measured difficulty
// band. Keeping the draw count constant preserves the existing stream.
freeApple() {
  const occupied = this.occupiedCells();
  let freeCount = 0;
  for (let y = 0; y < this.rows; y += 1) for (let x = 0; x < this.cols; x += 1) {
    if (!occupied.has(this.cellKey(x, y))) freeCount += 1;
  }
  if (!freeCount) return null;
  let index = Math.floor(Math.random() * freeCount);
  for (let y = 0; y < this.rows; y += 1) for (let x = 0; x < this.cols; x += 1) {
    if (occupied.has(this.cellKey(x, y))) continue;
    if (index === 0) return { x, y };
    index -= 1;
  }
  return null;
}
#+end_src

In English: walk the board and count the empty cells. Then pick a number between
zero and that count. Then walk the board again and stop at the *n*th empty cell.

The old version tested every cell of the board against every segment of the snake.
On a nearly full 60-by-44 board that is about seven million comparisons per apple,
and an apple appears every 80 milliseconds in the late game. The comment above the
function says the original was about 6.7 million.

And then the part that is genuinely remarkable. The comment explains that a *tempting*
alternative — picking a uniformly random free cell with the standard "reservoir"
trick — is worse, because it calls the random number generator once per free cell
instead of once per apple. That changes the sequence of numbers the difficulty
measurements consume, which silently moved the measured difficulty band. So they
kept exactly one draw. **The number of dice rolls is part of the contract.**

second. At a normal frame rate that drove the counter negative on the very first
frame, so the snake re-read the board every single frame — and the reaction delay,
which the whole difficulty design depends on, did not exist.

Then the choosing:

chooseDirection() {
  const head = this.snake[0];
  const believed = this.aiPerceivedApple;
  /* …remove the direction that would reverse into the neck… */
  // Scored against what the snake believes, not against the true apple.
  choices.sort((a, b) => this.routeScore(head, a, believed) - this.routeScore(head, b, believed));
  // Safety is decided by whether the cell is actually enterable, not by the
  // route score. Filtering on the score treated a cell inside the snake's own
  // body as safe, because that scores 5000 and the wall scores 10000 -- so the
  // snake would plan into its own tail and never once find itself with no
  // legal move.
  const safeChoices = choices.filter((direction) => this.canEnter(head, direction));
  const forced = safeChoices.length === 0;
  const candidates = forced ? choices : safeChoices;

  // Momentum: while a commitment is running the snake holds its heading unless
  // that heading is about to kill it. Without this it re-plans every move and
  // plays like a machine that can see the whole board.
  if (this.aiCommitLeft > 0) this.aiCommitLeft -= 1;
  if (this.aiCommitLeft > 0 && candidates.some((direction) => direction.x === this.direction.x && direction.y === this.direction.y)) {
    chosen = this.direction;
    held = true;
  } else {
    chosen = candidates[0];
    if (chosen.x !== this.direction.x || chosen.y !== this.direction.y) this.aiCommitLeft = this.aiTuning.commitMoves;
  }
  /* …record the decision… */
}

In English: score each legal direction by how much closer it gets to the *believed*
apple. Then throw away any direction that would actually kill it. If nothing is
safe, keep them all and take the best-scoring one, because a snake with no legal
move still has to move.

Then momentum: if a commitment is running and the current heading is still safe,
keep it. Do not re-plan. If you re-plan every move, the snake is a perfect solver
and there is no game left.

The trap in the middle comment is the good part. The scoring function returns 5,000
for "a cell inside my own body" and 10,000 for "off the board". So filtering by
score treats the body as *safer* than the wall. The snake would happily plan into
its own tail, and — the real damage — would never once be in a position with no
legal move at all. Which means a whole real game state was invisible to the
difficulty measurement. There is now a test for exactly that state, and its comment
says "it is a real state, not one the old scoring could even see."

In English: three reasons the computer misses, and none of them is a dice.

1. **It looks away.** Between 0.1 and 0.18 seconds it is thinking about where the ball
   will be, not moving. It commits to a direction when it looks and holds it.
2. **It is slow.** 600 pixels a second, and it moves in one-pixel steps toward a
   target rather than teleporting to it.
3. **It has limited foresight.** It traces the ball's path through *one* wall bounce
   and then gives up and sends the ball off in whatever direction it was heading.

And the dwell, which is the subtle one: after deciding to move left, it holds that
decision for between 0.18 and 0.38 seconds even if the ball changes its mind
mid-flight. Without the dwell, the paddle re-evaluates every frame and is very hard
to beat with a bank shot. With it, a committed misjudgement costs real time.

Versus mode is deliberately gentler and slower: 360 instead of 600, and a longer
rethink (0.18–0.28 instead of 0.1–0.18). The comment points at a document with the
measurements.

The foresight limit, as code:

#+begin_src js
// src/games/breakout/model.js:445-463 — trace one bounce, then give up
function predictBallX(ball, seconds, maxBounces = Infinity) {
  let x = ball.x;
  let velocity = ball.vx;
  let remaining = Math.max(0, seconds);
  let bounces = 0;
  while (remaining > 0) {
    const edge = velocity < 0 ? ball.radius : 800 - ball.radius;
    const distance = Math.abs((edge - x) / velocity);
    if (distance >= remaining) return x + velocity * remaining;
    x = edge;
    remaining -= distance;
    velocity *= -1;
    bounces += 1;
    // Out of foresight: carry the ball off in its current direction instead of
    // tracing its whole path. This is the limit that lets it be beaten.
    if (bounces > maxBounces) return x + velocity * remaining;
  }
  return x;
}
#+end_src

In English: work out where the ball will be in *n* seconds, assuming it bounces off
the side walls. Step forward in time to the first wall, flip the direction, keep
going. Stop after the allowed number of bounces, and from that point on just let the
ball travel straight.

The comment calls it what it is: "This is the limit that lets it be beaten." A player
who hits the ball at an angle that needs two bounces to return is playing against
something the computer cannot follow.

**What this buys:** Breakout's computer returns about 80% of balls and misses about
5–20% of them, and those misses happen in most sessions. A test asserts both, and
the comment explains why that combination matters: a per-decision dice would produce
misses scattered thinly across all sessions; a paddle with a limited view misses in
most sessions. So the *distribution* of misses is what proves the mechanism.

**The computer ball, which accelerates rather than snapping.**

// src/games/splat/model.js:406-440 — how the ball decides where to go
moveComputer(player, dt) {
  const column = this.columns.find((candidate) => {
    const passed = this.side === "race" ? player.passedColumns.has(candidate) : candidate.passed;
    return !passed && candidate.x > player.x;
  });

  const targetY = column.gapY + column.gapHeight / 2;
  /* …reaction and commitment clocks… */

  const difference = desiredY - player.y;
  // Acceleration rather than a velocity that snaps to the answer, so a late or
  // committed decision costs the ball time it does not have.
  const desiredVelocity = clamp(difference * this.aiTuning.velocityGain, -this.aiTuning.maxFall, this.aiTuning.maxFall);
  const change = clamp(desiredVelocity - player.vy, -this.aiTuning.thrust * dt, this.aiTuning.thrust * dt);
  player.vy += change;
}
#+end_src

In English: the ball works out the middle of the next gap, then *accelerates* toward
it, at most 620 pixels per second per second, and never falls faster than 360. It
does not teleport to the right height.

That last part is the whole difficulty. If the ball snapped to the gap, being late
would cost nothing. Because it accelerates, a decision made 0.1 seconds late means
the ball is still catching up when it arrives — which is where the deaths come from.
And because it *holds* a chosen gap rather than re-aiming every frame, being wrong
about one gap is expensive for a beat.

**What this buys:** a route that is 130-pixel-per-column vertical steps is cleared
about 45 times per run, loses about 1.1 lives per run, and finishes about 61% of the
time. Those are numbers from a hundred simulated runs, not opinions.

**The wrap, and the bug it caused.**

The board wraps: anything leaving the right edge appears on the left. Which means
two objects either side of the seam are one pixel apart, not 799 apart. Ordinary
subtraction says they are 799 apart, and every collision check, aim, and dodge
disappears exactly at the seam.

#+begin_src js
// src/games/asteroids/model.js:29-55 — four functions, and the reason they exist
// The board wraps, so an entity just past the left edge is one pixel from one
// just before the right edge. Plain differences report those as ~800 apart,
// which makes collisions vanish at the seam and aims and dodges take the long
// way round. Every distance in this model therefore goes through wrapDeltaX/Y.
export function wrapDeltaX(a, b) {
  let delta = a - b;
  if (delta > BOARD_WIDTH / 2) delta -= BOARD_WIDTH;
  if (delta < -BOARD_WIDTH / 2) delta += BOARD_WIDTH;
  return delta;
}
export function wrapDeltaY(a, b) {
  let delta = a - b;
  if (delta > BOARD_HEIGHT / 2) delta -= BOARD_HEIGHT;
  if (delta < -BOARD_HEIGHT / 2) delta += BOARD_HEIGHT;
  return delta;
}
export function wrapDistance(ax, ay, bx, by) {
  return Math.hypot(wrapDeltaX(ax, bx), wrapDeltaY(ay, by));
}
// Wrapped equivalent of circleHitsCircle: the closest approach between two
// wrapped circles may be across the seam rather than between their own centres.
export function wrapHitsCircle(ax, ay, ar, bx, by, br) {
  return wrapDistance(ax, ay, bx, by) < ar + br;
}
#+end_src

In English: the horizontal distance between two points is computed, and if it comes
out more than half the board width, subtract the whole board width. If less than half
a board *negative*, add the whole width. Then everything else — distance, collision,
aiming, dodging — is built on top of that.

The bug it fixes is beautifully specific and there is a test for exactly it, with the
comment "The issue's reproduction: one pixel apart through the seam." Two rocks at 793
and 7 are 786 apart by ordinary subtraction and 7 apart through the wrap. There are
fourteen tests for this one file's wrap behaviour.

Note the last function's comment: it is not enough to fix distance. Two circles

// src/games/asteroids/model.js:289-327 — the real fix, with all four bugs in the comments
if (distance < minimumDistance) {
  // Ships bounce. This used to point both ships away from each other and
  // teleport them apart, which overwrote each pilot's own heading and made
  // the computer look like it was dragging the human around. Now only the
  // velocity along the collision normal is exchanged -- the equal-mass
  // elastic result -- so a pilot who is not flying into the other ship is
  // left alone.
  const normalX = distance > 0 ? dx / distance : 1;
  const normalY = distance > 0 ? dy / distance : 0;
  // Relative velocity must include knockback already in flight. Measuring
  // thrust alone re-applies a full impulse every frame to two ships that
  // are already flying apart, which shakes them instead of bouncing them.
  const humanThrustX = Math.cos(this.ship.angle) * this.ship.speed + this.ship.knockX;
  /* …the same for the computer… */
  const closingSpeed = (humanThrustX - computerThrustX) * normalX + (humanThrustY - computerThrustY) * normalY;
  if (closingSpeed > 0) {
    const impulse = (1 + SHIP_RESTITUTION) * closingSpeed / 2;
    this.ship.knockX -= impulse * normalX;
    this.ship.knockY -= impulse * normalY;
    this.computerShip.knockX += impulse * normalX;
    this.computerShip.knockY += impulse * normalY;
  }
  // Still nudge them out of each other so they cannot sit overlapped; this
  // is a de-overlap, not the shove, and it never touches heading.
  const separation = (minimumDistance - distance) / 2;
  this.ship.x = (this.ship.x - normalX * separation + BOARD_WIDTH) % BOARD_WIDTH;
  /* …push the computer the other way… */
}

In English: four separate bugs in twenty lines, and the comments name each one.

1. **Don't overwrite headings.** If you are coasting and the computer bumps you, you
   keep going the way you were going.
2. **Only exchange velocity along the line between you.** Two ships of equal mass
   colliding head-on send each other back the way it came. Two ships grazing send
   each other off sideways. Nothing else changes.
3. **Count the knockback already flying.** The impulse calculation must include
   movement from the *previous* bounce, or two separating ships get a fresh full
   impulse every frame — which reads as shaking rather than bouncing. There are four
   tests for this, and they compare the impulses rather than the resulting speeds,
   with the reason spelled out: the steering pass has already decayed the speeds by
   the time you could measure them.
4. **The de-overlap is separate and does not touch heading.** If they are still
   overlapping after the bounce, move them apart by half the overlap each. That part
   is a numerical convenience, and the comment says so: "this is a de-overlap, not
   the shove." The old bug was adding the separation vector to the human ship rather
   than subtracting it, which drove both ships *through* each other — the same
   "dragging" symptom from the other side.

=SHIP_RESTITUTION= is 0.85: they keep 85% of their closing speed, so a graze bleeds
energy and cannot ping back and forth forever.

// Human-only budgets, independent of the flipped runner's perception/tuning.
// For a vertical star 160px above the runner (y340), allow 0.35s to react,
// 26/240s to clear the collision corridor, and one 60Hz frame of margin:
// vy <= (160 - 26) / (0.35 + 26/240 + 1/60) = 282.1px/s; round down to 280.
// Space spawns by reaction + a full 52px corridor crossing + one frame:
// 0.35 + 52/240 + 1/60 = 0.5833s; round up to 0.6s. This bounds pressure,
// not a guarantee against every random multi-star arrangement or late response.
const HUMAN_MAX_STAR_SPEED = 280;
const HUMAN_MIN_SPAWN_INTERVAL = 0.6;

export function starfallHumanDifficulty(score) {
  // Keep the original opening/first-gem ramp. Then ease toward the budgets
  // over two more gems (50 points each), with strict progression up to 150.
  const opening = Math.min(Math.max(0, score), 50);
  const later = clamp((score - 50) / 100, 0, 1);
  return {
    starSpeed: 130 + opening * 2 + later * (HUMAN_MAX_STAR_SPEED - 230),
    spawnInterval: 1.1 - opening * 0.006 - later * (0.8 - HUMAN_MIN_SPAWN_INTERVAL)

In English, and this is the clearest reasoning in the repository, so it is worth
following carefully.

The question: how fast can a falling star be before it becomes impossible to dodge
with a keyboard?

The answer, worked out in the comment:
- A star 160 pixels above you gives you 0.35 seconds to react. That is the budget
  for a human being who has not been watching the falling object since it spawned.
- It takes 26/240ths of a second to cross the collision corridor, because you move
  at 240 pixels a second and the corridor is 26 pixels wide.
- Add one frame of margin, because at 60 frames a second you cannot react inside the
  frame you are hit on.
- So: speed must be at most (160 − 26) ÷ (0.35 + 0.108 + 0.017) = 282.1 pixels a
  second. Round *down* to 280.
- For spawn spacing: 0.35 seconds of reaction, plus the time to cross the full
  52-pixel corridor (0.217s), plus a frame = 0.583 seconds. Round *up* to 0.6.

**Round down for the speed ceiling and round up for the time floor.** Both directions
are the safe ones. That is not an accident.

The comment's last sentence is the honesty clause, and it matters: "This bounds
pressure, not a guarantee against every random multi-star arrangement or late
response." The curve is a ceiling on pressure, not a promise that every layout is
fair.

// Providers may not reject promptly themselves. Race the signal too, and always
// unregister listeners when a successful request no longer needs cancellation.
export function abortable(promise, signal) {
  if (!signal) return Promise.resolve(promise);
  return new Promise((resolve, reject) => {
    const cleanup = () => signal.removeEventListener("abort", abort);
    const abort = () => { cleanup(); reject(abortError()); };
    if (signal.aborted) abort();
    else signal.addEventListener("abort", abort, { once: true });
    Promise.resolve(promise).then(value => { cleanup(); resolve(value); }, error => { cleanup(); reject(error); });
  });
}
#+end_src

In English: wrap a slow operation so that a cancel handle can end it. Three details
that each fix a real problem:

- **"Providers may not reject promptly themselves."** If the thing you are waiting for
  does not cooperate, this races a second outcome — the cancel — against it, so you
  are never stuck waiting for something that will not finish.
- **The listener is always removed.** Not only when cancelled. *Also* when it succeeds.
  A long-lived game that makes thousands of requests would otherwise accumulate
  thousands of listeners on one object. There is a test using Node's own
  `getEventListeners` to assert the count is exactly zero on every completion path.
- **Already-aborted is checked before listening.** Cancelling something that is
  already cancelled should reject immediately, not wait for an event that has already
  fired.

**The "did we already load it?" flag, which was a real bug.**

That comment about v6 is worth reading properly, because the old behaviour is a
genuine mistake you can reason about from first principles.

The old flag was: once the model has loaded, write "ready" into the browser's storage
so the next visit knows. Then on the next visit, if the flag says ready, do not
re-download.

**That is unsound**, and the comment says why in three clauses: the flag was either a
bare string, or a record with no version. Either way you cannot check *which* model
it was, or whether the model the browser has actually kept still matches the one you
would load today. Browsers evict cached data. So the flag could be true while
nothing was cached — and the site would believe it was ready and never load.

revision, and when. And =hasCachedModel= refuses unless all five match:

But each of them has its own cancel handle, and **the download is only abandoned when
the last of them has gone away.** If one caller cancels, the other still wants it, so
it keeps going. That is what "reference counted" means, and the test suite has
nineteen tests for it, including:

- "a shared model download aborts only when its last consumer leaves"
- "a finished request cannot cancel a later use of the shared engine" — finishing a
  request must not poison the shared model for subsequent requests
- "worker generation cancellation terminates compute and the next request reloads"

**The worker, and the one place where cancelling actually stops work.**

#+begin_src js
// src/ai/on-device.js:259-285 — requests, and what happens when one is cancelled
const engine = { device, cancelled: false, cancel, chat: ({ signal: requestSignal, ...payload }) => {
  if (requestSignal?.aborted) return Promise.reject(abortError());
  if (engine.cancelled) return Promise.reject(new Error("The local AI worker is unavailable."));
  return new Promise((requestResolve, requestReject) => {
    const entry = { id: ++sequence, payload, signal: requestSignal, resolve: requestResolve, reject: requestReject };
    entry.abort = () => {
      const wasActive = active === entry;
      if (wasActive) {
        active = null;
        // Only this request has been sent to the pinned runtime. Stopping
        // its worker really stops compute; queued consumers survive and
        // resume on a fresh worker using the same integrity-locked loader.
        retireWorker();
      } else {
        const index = queue.indexOf(entry);
        if (index === -1) return;
        queue.splice(index, 1);
      }
      settle(entry, abortError());
      if (!queue.length && !active && !workerReady) cancel();
      else pump();
    };
    queue.push(entry);
    requestSignal?.addEventListener("abort", entry.abort, { once: true });
    pump();
  });
} };
#+end_src

In English: there is a queue and one worker. One request at a time is being computed;
the rest wait their turn.

When you cancel:

- **If your request is the one running**, the worker is *terminated*. That genuinely
  stops the computation — a browser test asserts that cancelling during a real
  21-megabyte download actually closes the network connection, and that the retired
  worker sends no late messages afterwards. Waiting requests are not disturbed; the
  next one starts a fresh worker through the same fingerprinted loader.
- **If your request is still waiting**, it is taken out of the queue. Nothing else
  changes.

And there is one request at a time. A test asserts it with the message
"generation is serialized."

**What this file does not do**, and the doc says it plainly: it never downloads a
model from a branch name that could move, it never falls back to the public CDN, it
never runs code it has not fingerprinted, and it never claims that a failed
connection is a working one.

Verified 5 pinned AI assets (22451778 bytes).
#+end_src

Those four lines are worth reading as a unit, because each is a rule about the shape
of the code rather than about its behaviour. They are covered at the end of this
section.

**Read the test names as sentences.** They are the change's own summary of itself.
Grouped by what they are trying to pin down, and with the load-bearing ones quoted.

**** Group 1 — The computer opponents, and the no-dice rule

Six games, one **simulator** each — a small program that plays that game's rules
thousands of times with the dice fixed and counts what happened. Six test files assert
the counts fall in the right range, and two documents exist solely to define what is
being counted.

*simulator* is this document's plain word for what the repository calls a *Monte Carlo
fixture*. The tests call them fixtures.

The design principle is stated once, at the top of every one of the six AI defaults
objects, and it is the single most repeated sentence in the codebase:

#+begin_quote
// src/games/snake/model.js:7-9
// Snake computer factors. There is deliberately no chance of a wrong turn: the
// snake goes wrong because it has not looked at the board yet, or because it is
// already committed to a heading. Both are limits, not dice.
#+end_quote

And the consequence, which is what the tests actually verify:

#+begin_quote
// tests/ai/snake.test.js:15-17
// Not a perfect solver, and not randomly flailing either. Greedy stepping is
// the baseline, so this sits near half by construction; the point is that it
// is neither 0% nor 100%.
#+end_quote

In English: the computer snake takes a wrong turn somewhere between 25% and 70% of the
time, depending on how much room it has. That number is neither zero nor a hundred.
Zero would mean it cannot be beaten. A hundred would mean it is guessing.

And here is the best test in the repository, because it does not just check a band —
it identifies the *mechanism*:

#+begin_quote
// tests/ai/snake.test.js:40-43
// The mechanism, decomposed. Momentum is the factor that carries the mistake;
// with it removed and full knowledge restored, the snake is a perfect planner.
// If it were still wrong, the imperfection would be coming from somewhere the
// model cannot account for -- randomness, or a bug in this test's scoring.
#+end_quote

In English: they run the snake twice more. Once with its "hold a heading for three
moves" behaviour turned off and perfect knowledge restored. If it were *still* making
mistakes, the mistakes would have to be coming from something the test cannot account
for — a random number, or a bug in the test. Instead it is a perfect planner. So the
mistakes are the momentum, exactly as claimed.

That is an *explanatory* test, not a threshold test. It could only pass if the
mechanism is what the code says it is.

The other five, each with its own honest weakness:

| game | its stated weakness | the measured band |
|------|--------------------|--------------------|
| Snake | has not noticed the apple moved; holds a heading for three moves | 25–70% wrong turns; survives 25–70 seconds |
| Breakout | bounded top speed; one-bounce foresight; holds a misjudgement for a beat | returns >80%, misses 5–20%, and misses in most sessions |
| Splat | accelerates at 620px/s², so a late decision costs real time; commits to a gap | starting route: 100% cleared. Hard route: ~61% cleared, ~1.1 lives lost |
| Asteroids | turns at 3.6 rad/s; keeps aiming where it last looked; dodges in one of eight coarse headings | 0.05–0.4 losses per run; spends >20% of decisions swerving |
| Missile | the intercept estimate is short by 62% of the flight time | 40–75% of the attack gets through |
| Starfall | blind above y=300; re-reads on a clock; holds a lane | 45–80% of resolved threats dodged; collects 8–25% of gems |

Two of these deserve their quotes, because both are about *how* the difficulty arises:

#+begin_quote
// tests/ai/missile.mjs:4-7
// The per-shot hit rate is deliberately not the headline number. It falls as the
// battery fires more often, because each shot is spread thinner, while the number
// that matters -- how much of the attack actually gets through -- barely moves.
// So this measures both and pins the leak.
#+end_quote

In English: the obvious statistic — "what fraction of shots hit?" — is the wrong one,
because it falls whenever the computer shoots faster, regardless of whether it is any
better. The statistic that matters is the leak rate: how much of the incoming attack
gets past the defences.

And:

#+begin_quote
// tests/ai/breakout.mjs:3-4
// The paddle decides a direction rather than a coordinate, so the measurement is
// simple: how many balls did it get a paddle under, and how many went past.
#+end_quote

**The two documents.** =tests/ai/TUNING.md= (167 lines) and
=tests/ai/ACCOUNTING.md= (63 lines) exist because the tests above are meaningless
without definitions, and this project is not willing to leave that implicit.

=ACCOUNTING.md= opens with the sentence that justifies its existence:

#+begin_quote
An array shrinking or a score changing is not evidence of an interception, impact,
dodge, collection, or clearance.
#+end_quote

In English: four earlier baselines were measured wrong, because they counted things
that were not the thing being measured. So the document fixes each denominator:

- Asteroids counts only resolved life-loss events, and defines "proximity frames" as a
  rock within 105 pixels — explicitly *not* a count of collision opportunities.
- Missile leak rate is resolved attacks reaching their target over all resolved
  attacks, not as a percentage of launches.
- Starfall counts only threats projected into the runner's path within one
  commitment window, and the gem rate is collected ÷ (collected + passed).
- Splat counts the clearing event including the last one, and lets the Builder's own
  retry budget decide "unsolved."

The corrected baselines, in one table from the document, with the bands they replaced:

| fixture | runs | corrected baseline | band it must stay in |
|---------|-----:|--------------------|----------------------|
| Asteroids | 150 | 27 losses / 0.18 per run | 0.05–0.4 losses/run |
| Missile | 150 | 208 interceptions, 472 arrivals, 2,249 shots; 69.4% leak | 40–75% |
| Starfall | 150 | 62.1% dodged, 37.9% collided, 14.2% gem collection | 45–80% dodged |
| Splat, generated | 100 | 50 gates per run, zero losses, 100% solved | unchanged |
| Splat, hard | 100 | 45.4 clearances, 1.12 losses, 61% solved | unchanged |

=TUNING.md= is the other half, and it is a refusal as much as a reference. It
documents every computer's tunables and their defaults — then says:

#+begin_quote
These are headless model experiment seams, not UI settings or a new difficulty menu.
#+end_quote
#+begin_quote
Invalid configuration is not normalized or validated here.
#+end_quote

In English: you can hand a model a different difficulty from a test. There is no
difficulty menu, and deliberately none is planned. And if you hand it nonsense, it
does not tidy it up — the caller must supply meaningful values.

The document's best paragraph is about the separation between policy and accounting:

#+begin_quote
// tests/ai/TUNING.md:146-151
// Policy clearance (`laneWidth`) is deliberately distinct from actual collision
// radii. Starfall's outcome detector retains its original **fixed 0.95-second**
// collision-course horizon, independent of a tuned lane commitment. Otherwise a
// longer commitment would appear to improve dodge rate merely by reclassifying
// more unrelated stars as threats.
#+end_quote

In English: if you made the computer more cautious *and* counted its successes
more generously at the same time, the numbers would improve for the wrong reason.
So the measurement is pinned and cannot be tuned.

**Group 2 — Independent human input, and the refusal to call it fun**

=tests/player/= is eight files, and it is the most unusual thing in the repository:
hand-written input policies that play the games, kept strictly separate from the
computer opponents.

The separation is enforced structurally and it is the point:

#+begin_quote
// tests/player/harness.mjs:92-95
const position = ({ x, y }) => ({ x, y });
// Deliberately select fields; do not spread model/player/computer objects here.
// No timers, random state, AI fields, AI decision logs, or model methods are
// visible to the human-input policies.
#+end_quote

In English: the human player receives a snapshot with a dozen named numbers in it. It
does not receive the model object, so it *cannot* call an AI helper even by accident.
The comment says "deliberately."

And then the policies actively sabotage the production AI, to make sure:

#+begin_quote
// tests/player/policy-contract.test.js:21-23
const COMPUTER_HELPERS = ["chooseDirection", "routeScore", "canEnter", "refreshPerception", "aiShip", "moveComputer", "aiRunner", "visibleStars", "mostUrgentEnemy", "launchMachineInterceptor"];
// each is replaced with a function that throws
#+end_quote

In English: ten of the computer opponent's functions are replaced with ones that throw
an error if called. If a human baseline ever accidentally used one, the test fails
rather than silently producing an impressive number.

Then each policy is described by what it is *not* doing:

#+begin_quote
// tests/player/policies.mjs:33-34
// One-cell safety check and Manhattan apple chasing; no route search,
// flood fill, Hamiltonian cycle, future spawns, or AI route scorer.
#+end_quote
#+begin_quote
// tests/player/policies.mjs:87-89
// A bomber keeps dropping missiles: deal with it early unless a ground
// threat has already fallen below 250px. Ignoring all aircraft would be
// an artificially incompetent defender, not a useful human baseline.
#+end_quote

In English: each comment lists the sophisticated strategies it is avoiding, and the
second one goes further — it explains that being *too* bad is also wrong, because a
defender who ignores bombers entirely is not a measurement of anything.

That is the whole philosophy in one comment. A baseline that is too good measures the
game. A baseline that is too stupid measures the baseline.

**And then the honesty statement**, which appears at the top of the test file:

#+begin_quote
// tests/player/experience.test.js:8-9
// Broad mechanical guardrails. They are not a fun rating or population study.
// See docs/player-experience.md for hypotheses, denominators and calibration.
#+end_quote

And in the README:

#+begin_quote
These automated proxies do **not** establish subjective enjoyment or replace human
playtesting.
#+end_quote

In English, and it is worth being blunt about what this means: **this suite has
measured that the games are mechanically playable and have bounded difficulty. It has
not measured that they are any fun, and it says so in three separate places.**

What it *does* measure, per game: that doing nothing loses, that playing beats doing
nothing on score *and* survival *and* progress, that choices are spread through a round
rather than clustered at the start, that a near-miss has a recoverable window, and —
for Breakout and Splat — that a full clear is achievable in a bounded round.

That last one has the sharpest assertion messages in the suite:

#+begin_quote
// tests/player/completion.test.js
"a stalled clearance must remain a visible censor, not a victory"
"victory comes through the real lifecycle without a fabricated replenishment"
"score is not completion"
#+end_quote

In English: a game that reaches the time limit without finishing is *counted as not
finished*, and the test asserts the count of finished-plus-censored-plus-exhausted
equals the number of runs. The measurement cannot quietly turn a timeout into a win.

**Group 3 — The rules, edge by edge**

=tests/models.test.js= is 3,475 lines with 149 top-level tests, and its comment
header is the best argument for the whole approach:

#+begin_quote
// tests/models.test.js:20-23
// Several models roll Math.random during reset or on spawn, which makes any
// assertion about their contents flaky. Tests that assert on random output
// install a seed first so a failure means a real regression rather than an
// unlucky roll.
#+end_quote

In English: when a game picks random numbers, a test that fails might have found a
bug or might have got an unlucky roll. So the random number generator is fixed first,
and then a failure means a bug.

And this one, which is a fix you can feel:

#+begin_quote
// tests/models.test.js:2233-2235
// Fill the board to one cell short of full. This is the pathological case:
// the original nested scan was O(cells * snake length), so 2,640 cells x
// ~2,640 segments is about 7 million coordinate comparisons per apple.
#+end_quote

In English: at 60 by 44 the board has 2,640 cells. If finding a free cell means
testing every cell against every segment of the snake, that is about seven million
comparisons — and in the late game an apple appears every 80 milliseconds.

The performance test is unusual, and worth describing because the technique is
elegant: it keeps the *old* algorithm in the test file as a reference, times a handful
of its placements, and extrapolates.

#+begin_quote
// tests/models.test.js:2258-2261
// The original implementation, kept here as the reference point. It is
// O(cells * snake length): on this board ~2,640 cells x ~2,640 segments.
// Timing a handful of its placements and extrapolating keeps the test quick
// while still failing loudly if this regresses to the quadratic form.
#+end_quote

Then, because timing tests are flaky on a loaded machine:

#+begin_quote
// tests/models.test.js:2276-2278
// CPU contention/GC can pause either timing sample independently. Keep real
// timings visible, but gate the actual algorithmic improvement, not scheduler
// luck (this used to intermittently fail during parallel test execution).
#+end_quote

In English: the test measures how many times a property was *read* — an exact count,
no timing — and only *reports* the timings. And the property-read count is asserted to
under twenty. That is not a timing test that is a bit flaky; it is an exact test.

The other files in this group are more of the same, and the names are the summary:

- =breakout-retry.test.js= — 18 tests. Every combination of score and level and side
  checked for retained difficulty, plus the exact velocity of cloned balls.
- =breakout-outcomes.test.js= — 5 tests, all about the tie. "Branch order can never
  manufacture a winner."
- =asteroids-grace.test.js= — 7 tests on the respawn shield, including "a spent life
  protects against another hazard in the same frame."
- =splat-race-outcomes.test.js= — 4 tests, and the decisive one is named "fractional
  crossing time matters, not final x or human-first branch."
- =missile-objective.test.js= — 5 tests on scoring a destruction once, not repeatedly.
- =starfall-recovery.test.js= — 7 tests, and the difficulty table.
- =splat-builder.test.js= — 11 tests on the editor: preservation, the cap, the binary
  search, the gesture rules.
- =nonvisual.test.js= — 24 tests over the semantic adapter, run against a host built
  from the real engine with no renderer at all.

Three verified counts worth having on the record, because they are the ones a reviewer
will ask for. =tests/models.test.js= runs 149 top-level tests.
=tests/ai/tuning.test.js= is 513 lines that expand to 31 — six generated per model and
six per simulator, plus 19 written out longhand. =tests/imitation-contract.test.js= is
468 lines and runs 26.

**Group 4 — The contracts between parts**

Four files that check the seams.

=lifecycle-contract.test.js=, 16 tests, covering who owns a life and what raising and
lowering the setting does. Its method is worth noting — it builds a *real* engine on a
proxy that records every bit of text drawn:

#+begin_quote
// tests/lifecycle-contract.test.js:121
// Defensive boundary: even an already-paused terminal state cannot resume.
#+end_quote

=model-boundary.test.js=, 3 tests, and the third one is the most interesting test in
the suite as a *method*:

#+begin_quote
// tests/model-boundary.test.js
// a fresh Node process is spawned in which `window`, `document`,
// `requestAnimationFrame` and `cancelAnimationFrame` are defined as throwing getters
test("all arcade models import and step without a browser, renderer, or engine")
#+end_quote

In English: they start a brand new copy of Node where touching =window= or =document=
raises an error immediately. Then they import all six game models and play a step.
If any game rule so much as *looks at* the page, the process crashes.

That is how the "the model knows nothing about the browser" claim is enforced rather
than asserted.

=input-boundaries.test.js=, 8 tests, all with the same shape — for each of seven
context boundaries (stop, load, restart, side change, life loss, window blur, tab
hidden), assert that no held key, no pending press, and no half-finished pointer
gesture survives. And the negative case: a deliberate pause *must* keep them.

=core.test.js=, 23 tests, covering the engine itself. This is where the lives
asymmetry lives, with its assertions phrased as requirements:

#+begin_quote
// tests/core.test.js, lives group
"a raise never grants a free life now"
"raising again does not resurrect lives"
"unparseable input falls back to the default"
#+end_quote

**Group 5 — Cancelling work you no longer want**

=imitation-ai-cancellation.test.js=, 410 lines, 19 tests, and the technique is the
thing: it defeats Node's module cache by importing with a unique query string each
time.

#+begin_src js
// tests/imitation-ai-cancellation.test.js:19
const freshProvider = () => import(`../src/ai/on-device.js?cancellation-test=${++moduleSequence}`);
#+end_src

In English: Node remembers modules by path, so importing the same file twice gives
you the same object — including its remembered state. Adding a different query string
each time forces a genuinely fresh copy. Without that, the second test in the file
would silently test the first test's leftovers.

The assertions are the requirements, and they are unusually precise:

- "the other consumer still needs the download"
- "no consumer remains to own expensive work"
- "a late-created session is disposed, not leaked"
- "only active cancellation terminates compute"
- "a finished request cannot cancel a later use of the shared engine"
- "worker errors invalidate the cache"
- "no consumer remains to own expensive work"

Plus a structural check the whole time: using Node's own listener inspector to assert
that *zero* abort listeners remain on every completion path.

**Group 6 — The browser, driven remotely**

Five runners, none of them using a browser automation library. They speak the
browser's remote-control protocol directly over a socket, which is 1,663 lines of
hand-written client in =browser-smoke.mjs= alone.

What makes them valuable is stated in =README.md:141-147= — they drive the *real* page,
not a stand-in, with a fixed random number generator and a *manual clock*:

#+begin_quote
// README.md:141-147
// The browser suite drives a seeded `Math.random` and a manual clock, so it is
// deterministic rather than racing `requestAnimationFrame`: it cancels the queued
// boot frame before installing its virtual clock.
#+end_quote

And there was a bug in that, found and fixed:

#+begin_quote
// HANDOFF.md:41-45
// `e429c35`: cancels the native animation frame queued at boot before replacing
// RAF/cancellation. Otherwise it could arrive after virtual ticks and corrupt
// `dt`/cooldowns. A per-page clock assertion reproduces the pre-fix failure and
// passes after cancellation.
#+end_quote

In English: the page schedules its own animation frame at boot. The test then replaces
the clock. If the already-queued frame arrives afterwards, it computes a time step
from the *real* clock and corrupts the run. So the test cancels it first — and there
is a test that fails before the fix and passes after.

Three of those deserve a note.

**"native keyboard button activation without game side effects."** If you tab to the
*New game* button and press space, the browser activates the button — and the arcade
engine also sees a spacebar. The board would fire a missile. This suite asserts it does
not.

**"narrow viewport layout."** A 149-line stylesheet has to work at 375 and at 320
pixels. It does, and the test checks the page does not scroll sideways.

**The one that refuses.** Every runner has this:

#+begin_src js
// tests/nonvisual-browser.mjs:5
if (new URL(origin).port === "9223") throw new Error("Refusing Electron debugging port 9223; use dedicated Chromium.");
#+end_src

In English: port 9223 is the author's own desktop application. These tests connect to
a browser and can close its tabs and change its settings. So they refuse to run against
that port.

There is a *test* for the refusal, which spawns a fake server reporting a desktop
user-agent and asserts the runner exits with an error and — this is the assertion that
matters — that it opened **zero** control connections:

#+begin_quote
// tests/browser-ownership.test.js
upgrades === 0   // "never opens the desktop control WebSocket"
#+end_quote

In English: it does not merely refuse *after* connecting. It refuses before.

**Group 7 — Security and supply chain, asserted as facts about files**

Three files that read the repository's own configuration and assert things about it.

=security-headers.test.js= parses =_headers= and pins the entire policy. Every
directive is asserted, and the three that are *absent* are asserted absent too —
=unsafe-inline=, =unsafe-eval=, and jsDelivr. Plus two rules that are easy to get
wrong:

#+begin_quote
// tests/security-headers.test.js
// no upgrade-insecure-requests, because "Ollama intentionally uses trustworthy HTTP loopback"
// Strict-Transport-Security: max-age=31536000 with no includeSubDomains and no preload
#+end_quote

In English, both are refusals. Upgrading every request to HTTPS would break the local
model program, which by design listens on plain HTTP on your own machine — and that is
fine, because it is loopback and cannot leave your computer. And the HSTS setting covers
this game only, not subdomains, and is not preloaded: this project does not get to make
that decision for a domain it shares.

=csp-evidence.mjs= is a classifier with a refusal as its reason to exist:

#+begin_quote
// tests/csp-evidence.mjs:1-3
// Cloudflare can inject optional Web Analytics only for browser requests.
// The self-only executable policy intentionally blocks it; never whitelist it
// in script-src or accept a report-only violation as proof of enforcement.
#+end_quote

In English: the hosting provider injects an analytics script. The site's policy blocks
it — on purpose. So the classifier knows about exactly one expected violation, from
exactly one provider, on exactly one production address, and treats every other
violation as a failure. And its test feeds it five near-misses, including a
look-alike domain:

#+begin_quote
// tests/csp-evidence.test.js
// static.cloudflareinsights.com.evil.example/beacon.min.js
#+end_quote

=a i-runtime.test.js= is the supply-chain file, 70 lines, 7 tests, and it is the most
paranoid document in the repository:

- Every vendored executable file's fingerprint must match =vendor/ai/manifest.json=.
- An *extra* executable file in that folder is a failure: "Unreviewed executable."
- The actual browser library is executed in a synthetic environment with a linker that
  throws on any import: so it cannot be importing something remotely.
- The 21MB engine is verified, instantiated, and executed for real.
- A fingerprint failure must be caught *before* the bytes are compiled.
- Every import in =src/ai/= must be a relative path.

And =ollama-origin-docs.test.js= exists to stop a *document* from lying, which is
almost certainly the most unusual test in the repository:

#+begin_quote
// tests/ollama-origin-docs.test.js:1-11
// The deployed site cannot reach a local Ollama server, and the automated suite
// cannot prove it either way because it serves from a loopback origin.
//
// Ollama answers only loopback origins by default, and the deployed origin is
// additionally blocked by Private Network Access, which requires an
// Access-Control-Allow-Private-Network header Ollama never emits. Setting
// OLLAMA_ORIGINS clears the CORS gate and still fails.
//
// So these tests do not attempt to prove connectivity. They assert the one thing
// that regresses silently: that the documentation keeps stating the real limit
// rather than quietly claiming a fix that does not work.
#+end_quote

In English, and read the last paragraph twice, because it is a rare and admirable kind
of test: **the authors could not prove a thing, so they wrote a test that proves they
are still admitting they cannot prove it.**

**Group 8 — The four static checks, which are rules about shape**

These are not tests of behaviour. They are tests of architecture, and they are the
mechanism by which every other guarantee in this document holds.

**=scripts/check-model-boundary.mjs=**, 45 lines. Walks the entire dependency graph of
all six board-game models — including re-exports and dynamic imports — and refuses
anything not on a list of eight allowed files. Then it greps the allowed files for
references to the browser, for drawing calls, and for the word =engine=. And then it
checks the *other* direction:

#+begin_src js
// scripts/check-model-boundary.mjs:37-38
const engine = await readFile(resolve(root, "src/engine.js"), "utf8");
if (/\b(?:this\.)?game\.(?:id|snake|engine)\b/.test(engine)) throw new Error("Engine knows a concrete game identity, state, or backreference");
#+end_src

In English: **the cabinet body must not know any game's name.** Not Snake's id, not a
Snake field, not a back-reference to the engine. The comment above the function says
why the graph walk exists: "so putting the host behind a nominally neutral helper
cannot bypass the check." Someone tried that, and the check was written to close it.

**=scripts/dead-code-check.py=**, 91 lines, in Python, in a JavaScript project, and
its docstring explains itself:

#+begin_quote
This is intentionally a small grep-style check rather than a full linter:
it runs with no dependencies and matches the framework-free, no-build
nature of the project.
#+end_quote

It finds two kinds of debt: CSS classes nobody references, and exports from
=src/engine.js= that nothing imports or tests. Its method for the second is worth
noting:

#+begin_quote
// scripts/dead-code-check.py:51-59
Counting occurrences rather than testing membership is deliberate: the
declaration itself contains the name, so a plain membership test
against the full source would mark every export as referenced. A live
helper is named at least twice -- once at its declaration and once
where it is used, imported, or tested.
#+end_quote

**=scripts/check-readme-controls.mjs=** — 83 lines. Reads the README's controls table
and compares it against what the controllers actually report, in all twenty modes. It
is what stops the README from becoming the seventh thing that lies. Its output is the
third line of the check run at the top of this section.

**=scripts/vendor-ai-runtime.mjs=** — 71 lines. Verifies the five pinned files' sizes
and fingerprints, and can reconstruct them from locked archives with
=--restore=, verifying the archive checksum first and never regenerating an expected
hash.

**What the whole suite is, in one paragraph**

It is 470 checks in ten seconds plus five browser runners, and it covers: every game
rule at its edges; every computer opponent's difficulty as a number with a documented
denominator; every claim the page makes about itself; the security policy as text on
disk; the provenance of a 22-megabyte third-party dependency; and the honest limits of

browser connection exercise, no real model inference, and no claim of enjoyment.

* Four defects found in this document's own subject, and fixed

Four things were reported against the running cabinet while this document was being
written. Three were ordinary bugs. The fourth was a feature that should never have
shipped. All four are described here so that the sections above, which quote the
current code, can be trusted.

**1. Choosing a different mode started the game immediately.**

Switching the "You control" dropdown from Solo to You-vs-computer dropped the player
straight into a live round. No countdown, no ready screen, no chance to read what
just changed. The engine's =setSide= had cleared the ready and stopped flags, and
the combination "neither flag set" is exactly what "running right now" means.

The fix is that =setSide= now asks the same question =load= asks — does this game
declare interactive boot? — and holds at READY otherwise. That is not a new rule.
Clicking a different game card has always worked correctly, and choosing a different
mode is the same event. Imitation, the one game that declares interactive boot,
correctly never waits.

**2. The arrow keys did nothing until you clicked the board.**

Every control on the page keeps keyboard focus after you use it. Press *New game*
and the focused element is the New game button — and the engine's key handler, quite
deliberately, hands any key to a focused control. The result was a dead keyboard:
the board answered nothing until the player discovered that clicking the board was
the way out.

The tempting fix was to take focus back for the board. That would have been one
line, and it would have been wrong: it moves focus away from the button the player
just pressed, out from under anyone navigating without a mouse. The fix instead
carves out an exception, and only an exception. Buttons do not use arrow keys, so
the four arrows now reach the board even while a button, link, or =role= button=
holds focus. Space and Enter still activate the button natively, letters still stay
out of the round, and selects and text entry still keep everything they own.

**3. and 4. The "Canvas labels (full size)" panel, and the shuffling it caused.**

Underneath the board there was a bulleted list, headed "Canvas labels (full size)",
containing a copy of every piece of text drawn on the board that frame. It appeared
whenever any label would be smaller than 12 real-world pixels — which, on an
800-pixel board, includes Breakout's 7-pixel brick badges even on a full-width
desktop. It had been added for a real reason, and the reasoning was sound: a 12-pixel
label on a board scaled to a phone really is about 5 pixels tall, and unreadable.

But the panel cost more than it bought, and the reasons are all mechanical:

- It listed *whatever had been drawn that frame*. Scores, lives, countdown text and
  brick labels appeared, reordered and vanished sixty times a minute. On Breakout it
  looked like the list was shuffling on its own, which is precisely what it was.
- It changed the height of the page, and the board's width is =min(100%, 68.57vh)=.
  Crossing the viewport height toggled the scrollbar, which changed the viewport
  width, which rescaled the board, which could push a label back over the 12-pixel
  threshold and hide the panel again. A feedback loop, driven by its own contents.
- It was marked =aria-hidden="true"=, so it was never the semantic channel a screen
  reader reads. It duplicated text that already lived in the DOM — the score, the
  lives, the status line — without replacing any of it.
- Its heading was internal jargon, printed in the middle of a game.

So it is gone. =src/rendering.js= went from 95 lines to 29 and is now pure drawing:
it creates no elements and inserts none, at any board width or any label size. The
tests now assert that absence directly, in unit tests and in the real browser, in
both the ready and the running posture, and they assert that forty drawn frames
leave the page's geometry byte-identical.

**What this gives up, stated plainly.** Breakout's power-up labels are still 7 pixels
tall and still unreadable on a phone, and Missile Command's batteries are still
labelled with a bare letter and a bare number. A better answer than the withdrawn
panel would be to make the labels genuinely larger, but that overlaps the playfield
on a narrow screen, and it is a design change rather than a bug fix. It is left open
rather than papered over, and it belongs with =src/nonvisual.js= and with human
testing, not with a panel that reflows.

**=_headers= — six lines, and they are the security policy.**

#+begin_src
/*
  X-Content-Type-Options: nosniff
  Referrer-Policy: strict-origin-when-cross-origin
  Strict-Transport-Security: max-age=31536000
  Content-Security-Policy: default-src 'self'; script-src 'self' 'wasm-unsafe-eval'; worker-src 'self'; style-src 'self'; connect-src 'self' https://huggingface.co https://*.hf.co http://127.0.0.1:11434 http://127.0.0.1:11435 http://localhost:11434 http://localhost:11435; img-src 'self'; font-src 'self'; object-src 'none'; base-uri 'none'; frame-ancestors 'none'; form-action 'self'
  Permissions-Policy: camera=(), microphone=(), geolocation=()
#+end_src

In English, one at a time, because each one is a different kind of protection:

- **=nosniff=** — do not guess a file's type from its contents.
- **=strict-origin-when-cross-origin=** — do not leak the page address to other sites
  except when actually navigating there.
- **HSTS for one year** — always use HTTPS from now on.
- **=script-src 'self' 'wasm-unsafe-eval'=** — the page may run its own scripts and
  may compile WebAssembly, and *nothing else*. Not another domain, not an inline
  script.
- **=worker-src 'self'=** — background helpers must come from this site.
- **=connect-src=** — the page may talk to itself, to the model host for model
  *data*, and to four addresses on your own machine. Nothing else.
- **=object-src 'none'=, =base-uri 'none'=, =frame-ancestors 'none'=** — no plugins, no
  base-tag tricks, and this page cannot be embedded in anybody's frame.
- **=form-action 'self'=** — no form can post anywhere else.
- **=Permissions-Policy:=** — this game does not want your camera, microphone, or
  location, and it says so.

The `'wasm-unsafe-eval'` is the interesting one. It is a deliberate, narrow exception:
the local AI runtime compiles WebAssembly, and browsers block that by default. The
value grants exactly that and nothing broader. =docs/ai-runtime.md= spells out the
distinction — it is "not unrestricted =unsafe-eval=, jsDelivr, or arbitrary
third-party script hosts."

And the four loopback addresses are there because two of the four AI providers run on
your own machine. Which, as *Contradictions* item 6 explains, works when you serve the
site locally and cannot work from the public site.

reasoning paragraph in every file section. It is not captions without pictures.

**I ran what I could.** All 470 Node tests pass in ten seconds. All four static checks

local server, and this is not my machine. Everything in this document about the browser
suites is read from the source, from the README, and from the handoff record.

**Four things this document cannot tell you, and does not pretend to.**

**Nobody has established that these games are fun.** The suite measures mechanical
playability and bounded difficulty with real numbers. It says in three separate places
that it is not measuring enjoyment. =docs/player-experience.md= contains a manual
playtest procedure — which means the authors know what is missing and have written
down how to fill it. Nobody has filled it.

**The separate-browser connection has never been exercised by a person.** The code is
there, the automated tests cover it with a fixture and with two browser contexts, and
=HANDOFF.md= says plainly that a real WebRTC exchange between two machines remains
outside the verification. Copying a connection code between two browsers by hand, on
two different networks, is a different thing from a test that does it in one browser.

**No real model has been run through this repository's own verification.** There are
about 2,600 lines of tests for the AI subsystem and Imitation's networking, and almost
all of them use a *stand-in* — a fake Chrome, a fake fetch, a fake worker. The genuine
article tests do exist and are
good: the vendored runtime really executes, the fingerprint is really checked before
compilation, a cancelled download really closes its connection in a real browser. But
a 1.7-gigabyte model download and real inference are a manual gate, and the README
says so. Also, and this is worth being plain about: the model is a small local Llama,
and =REFERENCE_NOTES.md= is careful to note it is not what one might assume.

**The 21-megabyte dependency is reviewed at its boundary, not throughout.** The
document says what was checked and what was not, and it is honest on both counts.

Everything else — all 48 source files, all 64 test files, the security policy, the
