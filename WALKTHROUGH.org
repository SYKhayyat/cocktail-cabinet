* Read this part even if you read nothing else

** It is one machine, not seven

The Cocktail Cabinet is a website with seven games in it. But it is not seven programs
that happen to sit on the same page. It is *one* program with seven different things
loaded into it.

The way to picture it is an arcade cabinet from the nineteen-eighties. The cabinet is
always the same cabinet: the same screen, the same joystick and buttons, the same coin
slot, the same power supply, the same clock ticking the same speed. What changes is the
game you put in. The cabinet supplies power, controls and a screen. The game supplies
the rules.

That is exactly how this codebase works, and the picture does all the work:

| In the arcade cabinet                                | In this codebase                        |
|------------------------------------------------------+-----------------------------------------|
| the cabinet body, screen, joystick, power            | =src/engine.js=                           |
| the game cartridge                                   | =src/games/<name>/model.js=               |
| the label on the drawer saying which cartridge is in | =src/main.js=, the "You control" dropdown |
| the drawers down the left side of the machine        | =index.html=, the seven game buttons      |

The consequence, and it is the one thing to know before reading any file: *no game file
knows that the other six exist.* There is no shared "Game" parent class. There is no
list of the games that the games themselves can look at. Each of the seven is written from scratch, and
the only thing that holds them together is that they all answer the same short list of
questions by name.

**Where the cabinet body lives, and why it matters**

The cabinet body is =src/engine.js=, 323 lines. It owns the drawing rectangle, the
keyboard and mouse listeners, and the once-per-frame loop. It is the only place in the
repository that knows what a "frame" is.

Here is the whole idea in one function. It is the loop that runs about sixty times a
second. It asks the loaded game three questions per tick — take one step, paint yourself,
and tell me your words for the player — and then reports the score back to the page:

#+begin_src js
// src/engine.js:180,216,242-243 — the three questions, asked sixty times a second
this.game.update(delta, this.input);
/* ELIDED src/engine.js:181-215 — 35 lines: what to do when the game says it won, or
   that a life was lost. Counted down, cleared, and handed back to the game. */
this.game.draw(this.context);
/* ELIDED src/engine.js:217-232 — 16 lines: the dark READY / PAUSED / OUT OF LIVES box,
   drawn by the cabinet body on top of whatever the game just painted. */
this.onState?.(this.game.publicState());
this.onScore?.(this.game.score);
#+end_src

Everything else in the repository is an answer to one of those three questions. Both gaps
above are described in full further down: the first is the cabinet body's default
life-loss handling, under *And the reverse half of the trick*; the second is the box it
paints over the game, under *The overlay, which is drawn by the cabinet body and not by
any game*.

**What the cabinet does all day**

1. The page opens. =src/main.js= immediately builds all seven games and puts a button for
   each one down the left side.
2. Snake loads. The engine paints a dark rectangle with a box on it that says READY.
3. Nothing moves, because the cabinet is waiting to be told to start.
4. The human presses *New game*. A countdown runs for three seconds.
5. Then the loop starts doing real work, sixty times a second, until the human loses.
6. The human clicks a different drawer. The same loop keeps ticking. Different cartridge.
7. Six of the seven are board games. The seventh, Imitation, has no board at all. It has a
   chat box, and it runs its own timer inside the same loop.

**The one mismatch that will confuse you fastest**

The left-hand dropdown promises some games are "You vs computer." For four of them that
was not true. Breakout's default, Splat's default, Asteroids' default and Starfall's
default had no computer opponent anywhere in them. The computer code in those files only
runs when you pick the *other* option from the same dropdown.

A player opened the cabinet, was told they were playing a machine, and there was no
machine. That was fixed on 2026-09-25 in commit =351aba5= by changing four strings of
text and nothing else. You can see both versions in the Contradictions section.

**The whole change in one sentence**

The codebase is one shared machine with one fixed list of questions, asked of seven games
that each answer it differently, held together by a deliberately loose agreement rather
than by a shared parent class.

Everything below is that same idea in more detail.

* The glossary

Ten words. Every one is defined here before it is used anywhere else in this document.

**1. Cabinet**
The whole web page as a physical machine: the screen, the buttons, the drawer list, the
score box. You can see all of it in =index.html= and =styles.css=.

**2. Cartridge**
One game's rules, on their own, with no knowledge of the cabinet or of each other. There
are seven. Each lives in a file called =model.js=.

**3. The cabinet body**
=src/engine.js=. The part that owns the drawing rectangle, the keyboard and mouse, and
the sixty-times-a-second loop. One of them, shared by all seven cartridges.

**4. Side**
Which job the human does in a given game. "Steer the snake" or "place the apples".
"Side" is the one word in this codebase that means two opposites at once, and every game
handles it the same way: pick a side, and the game behaves differently.

**5. A step**
One tick of the loop, sixty times a second. Not one game move — in Snake, for example, the
snake moves once every *six* steps or so, on a clock of its own.

**6. The front counter**
The thin wrapper around each cartridge, in each game's =index.js= file. It holds the
cartridge and a translator, and exposes them under the names the cabinet body expects. It
contains no rules of its own. Seven of them, all near-identical.

**7. The translator**
Each game's =controller.js= file. Its whole job is turning key presses and mouse
positions into the words the cartridge understands, so that the cartridge never has to
know what a keyboard is.

**8. The painter**
Each game's =view.js= file. It draws the picture and nothing else. It holds no state and
never changes anything. Six of them, all near-identical in shape.

**9. Canvas**
The rectangle the game is drawn inside. 800 pixels wide, 560 tall, fixed for every game.

**10. The agreement**
The unwritten list of names the cabinet body asks for. Nine of them every game must
supply. Sixteen more it asks for only if the game happens to have them, and it carries on
either way. That tolerance is the single design decision that makes seven independent
games possible in under four thousand lines.

* The story

**What the cabinet does, minute by minute**

1. =index.html= loads. It contains the drawer list, the score box, the lives box, the
   controls, the chat panel, and one empty rectangle. The drawer list is empty.
2. =src/main.js= runs. It builds all seven games at once, in a list. Building a game means
   creating its cartridge, its translator and its front counter. No game starts.
3. It fills the drawer list with seven buttons and loads Snake, which is the default.
4. The cabinet body starts its loop. The loop paints. But because the cabinet is
   "ready", it will not let the game take a step. It paints the board and a box on top
   saying READY and *Press New game to start*.
5. The human presses *New game*. A three-second countdown runs. Nothing can be done
   during it.
6. Then, sixty times a second, the loop asks Snake to take one step and to paint itself.
7. Snake's translator turns the arrow keys into a direction and the mouse into a point on
   the board, and hands them to the cartridge.
8. The cartridge moves the snake one square, checks whether it hit a wall or itself, and
   if it did, sets a single flag saying a life was lost.
9. The cabinet body sees the flag, takes one off the lives counter, tells the cartridge to
   put the pieces back, and runs another three-second countdown.
10. After the last life, the cabinet stops and says *Out of lives*.
11. The human clicks a different drawer. A different cartridge is loaded into the same
    cabinet. The loop never stopped.
12. If the human picks Imitation instead, the cabinet hides the rectangle entirely, hides
    the score box, hides the *New game* button, and shows a chat panel instead. Imitation
    still runs inside the same loop, sixty times a second, using its own clock for things
    like "how long until I give up waiting for the other player".

**The thing to know before reading any cartridge**

The computer opponent is not a separate program. There is no second copy of the rules and
no cheat code anywhere in this repository. The computer reads the same positions, obeys
the same collision checks, and can genuinely lose — the tests prove it loses on purpose
often enough to measure.

This is deliberate and it is written down. Here is the original plan, unchanged:

#+begin_quote
The machine code makes decisions from current positions and collision state. It does not
skip a round, award itself points, or bypass collision checks.
#+end_quote
-- =PLAN.md=, section *Game rules*

The way that is guaranteed in Snake is worth seeing, because it is the clearest example
in the codebase. The computer picks a direction using a scoring function, and then that
direction is fed into the *same* collision code the human's moves go through. There is no
second collision check.

#+begin_src js
// src/games/snake/model.js:117-121 — rank every legal turn, drop the suicidal ones, pick
choices.sort((a, b) => this.routeScore(head, a, apple) - this.routeScore(head, b, apple));
const safeChoices = choices.filter((direction) => this.routeScore(head, direction, apple) < 10000);
const candidates = safeChoices.length ? safeChoices : choices;
this.nextDirection = Math.random() < AI_MISTAKE_CHANCE ? candidates[Math.min(candidates.length - 1, 1 + Math.floor(Math.random() * Math.max(1, candidates.length - 1)))] : candidates[0];
#+end_src

And the scoring it ranks by. Off the board scores 10,000. Into its own body scores 5,000.
Anything legal scores its straight-line distance to the apple, which is the most you could
possibly get. Sorting ascending therefore puts the best move first, and 10,000 — the
filter on line 119 — throws away every move that ends the game:

#+begin_src js
// src/games/snake/model.js:123-130 — how the computer rates one possible turn
routeScore(head, direction, apple) {
  const next = { x: head.x + direction.x, y: head.y + direction.y };
  const x = this.wrap ? (next.x + this.cols) % this.cols : next.x;
  const y = this.wrap ? (next.y + this.rows) % this.rows : next.y;
  if (x < 0 || x >= this.cols || y < 0 || y >= this.rows) return 10000;
  if (this.snake.some((part) => part.x === x && part.y === y)) return 5000;
  return Math.abs(x - apple.x) + Math.abs(y - apple.y);
}
#+end_src

Notice what is *not* in that function. It never awards a point, never moves the snake, and
never checks whether the apple is reachable. It only returns a number. The chosen
direction is stored in =nextDirection=, and on the next pass through the same method that
the human's arrow keys write to, it is copied into =direction= at line 87. From line 89
onward, human and computer are indistinguishable. That is the entire mechanism behind the promise in =PLAN.md=.

* Contradictions

Five places where something in this repository disagrees with something else. In every
case the code is what runs, and in every case the code wins. This section exists so that
you do not lose forty minutes to any of them.

**Verdict, stated once: trust the code, every time.**

**1. The plan describes a structure the repository no longer has**

=PLAN.md= is titled *first draft plan* and says so. It describes =src/games/*.js= as
"one self-contained game per file". There are seven such files, one line each, and they
do nothing but point somewhere else. The real games are seven directories of four files
each. The directory split happened in commit =80a59d8=, *Refactor games into MVC and
expand tests*.

=PLAN.md= also promises an =AiController= interface as the seam between games and AI. That
name appears nowhere in the repository. There are no AI opponents behind any interface;
the six arcade games have plain JavaScript in their own files, and only Imitation touches
anything under =src/ai/=.

=PLAN.md= also says "Each of the three GitHub repositories has a push workflow". This
repository has exactly one workflow, and it deploys only this repository.

> Trust the code. The plan is accurate about intent and stale about shape, and it says
> *first draft* on line one.

**2. The plan promises five names. The cabinet body asks for twenty-five.**

=PLAN.md=, section *Game rules*, states the agreement in five lines:

#+begin_quote
Every game exposes the same small contract:
- =reset()= starts a fair round.
- =update(delta, input)= advances real game state.
- =draw(context)= renders the current state.
- =setSide(side)= changes which side the human controls.
- =publicState()= supplies UI text.
#+end_quote

The cabinet body actually uses twenty-five names. Nine of them every game must supply,
and sixteen that only some games supply. This is not a plan that was broken. It is a plan
written before the seventh game existed, and the design grew to cover more ground than
five names could hold. The full verified matrix is in the =src/engine.js= section below.

> Trust the code. It is the only description of the agreement that is still true.

**5. =src/ai/on-device.js= — how Imitation finds a language model to talk to, without an account or a key.**

Only one of the seven games touches this file. The other six have their opponents written
in plain JavaScript inside their own folders. This file exists for Imitation alone.

Its whole job is a ladder of four ways to get a language model, tried in order, taking
whatever works first. It never asks for a password, never calls a paid service, and never
sends a message anywhere except the player's own machine.

The four rungs, in the order they are tried:

| Rung | What it is | When it is used |
|---|---|---|
| 1 | Chrome's own built-in AI, if the browser has one | First, always attempted |
| 2 | Ollama, a program the player may have installed | Second, on four local addresses |
| 3 | A model running on the graphics chip, via WebGPU | Third |
| 4 | A model running on the processor, in a background helper | Last resort, always works |

**Flying: the two input schemes, and why they behave differently**

#+begin_src js
// src/games/starfall/model.js:23-38 — pushing gems apart, pairwise, every frame
separateGems() {
  for (let first = 0; first < this.gems.length; first += 1) {
    for (let second = first + 1; second < this.gems.length; second += 1) {
      const left = this.gems[first];
      const right = this.gems[second];
      if (left.remove || right.remove || left.collected || right.collected) continue;
      const dx = right.x - left.x;
      const dy = right.y - left.y;
      if (Math.abs(dx) >= 90 || Math.abs(dy) >= 45) continue;
      const direction = dx === 0 ? (first % 2 ? 1 : -1) : Math.sign(dx);
      const push = (90 - Math.abs(dx)) / 2;
      left.x = clamp(left.x - direction * push, 0, 800);
      right.x = clamp(right.x + direction * push, 0, 800);
    }
  }
}

**The computer's targeting: the most considered AI decision in the repository**

This is what =issues.md= calls the Starfall runner AI *"safe and predictable"*, and the

Read it as four questions: which gems are worth going for; should I switch; which of seven

#+begin_src js
// src/games/starfall/model.js:112-145 — the whole computer runner
aiRunner(dt) {
  const activeGems = this.gems.filter((gem) => !gem.collected && gem.y <= this.runner.y + 50);
  this.aiTargetLock = Math.max(0, (this.aiTargetLock || 0) - dt);
  if (!this.stars.length && !activeGems.length) return;
  const gemCost = (gem) => Math.abs(gem.x - this.runner.x) + Math.abs(this.runner.y - gem.y) * 0.15;
  const rankedGems = [...activeGems].sort((first, second) => gemCost(first) - gemCost(second));
  let targetGem = rankedGems.find((gem) => gem === this.aiTargetGem);
  const targetIsSafe = this.aiTargetX === null || this.stars.every((star) => Math.abs(this.aiTargetX - star.x) > 45);
  if (!targetGem || !targetIsSafe) {
    targetGem = rankedGems[0] || null;
    this.aiTargetLock = 0.45;
  } else if (!this.aiTargetLock) {

    const betterGems = rankedGems.filter((gem) => gem !== targetGem && gemCost(gem) < currentCost - 25);
    const roll = Math.random();
    if (betterGems[0] && roll < 0.5) targetGem = betterGems[0];
    else if (betterGems[1] && roll < 0.8) targetGem = betterGems[1];
    else if (betterGems[2] && roll < 0.9) targetGem = betterGems[2];
    this.aiTargetLock = 0.45;
  }
  const candidates = [20, 160, 300, 440, 580, 720, 780];
  const safe = candidates.filter((candidate) => this.stars.every((star) => Math.abs(candidate - star.x) > 45));
  const pool = safe.length ? safe : [this.runner.x < 400 ? 20 : 780];
  const target = pool.reduce((best, candidate) => {
    const distance = targetGem ? Math.abs(candidate - targetGem.x) : Math.abs(candidate - this.runner.x);
    return distance < best.distance ? { x: candidate, distance } : best;
  }, { x: pool[0], distance: Infinity });
  if (this.aiTargetX === null || !targetIsSafe || this.aiTargetGem !== targetGem) {
    this.aiTargetX = target.x;
    this.aiTargetGem = targetGem;
  }
  if (Math.abs(this.aiTargetX - this.runner.x) <= 4) this.runner.x = this.aiTargetX;
  else this.runner.x = clamp(this.runner.x + clamp(this.aiTargetX - this.runner.x, -1, 1) * 300 * dt, 20, 780);
}
#+end_src

Five decisions in there, and each one is a fix for a specific complaint:

Line 113 — only chase gems that are *at or above* the runner. A gem that has already fallen
past you is not worth turning around for.

Line 116 — the cost of a gem is its horizontal distance plus its vertical distance times
0.15. That factor of 0.15 is the whole weighting: a gem straight below you but far away is
worth less than one beside you but higher up. Vertical distance is deliberately cheap.

Lines 118 to 123 — **the lock**. Once the computer picks a gem, it commits for 0.45
seconds. Line 120 is the override: if the position it is heading for is no longer safe, it
abandons the lock immediately. So it cannot be stubborn about a spot a star is falling into,
but it will not dither between two nearly-equal gems either.

Lines 124 to 130 — and this is the cleverest part. When the lock expires, the computer
looks for a gem that is *meaningfully* better — line 125 requires a cost improvement of
more than 25, not merely any improvement — and then switches to it with a **weighted
choice**: 50% chance of the best one, 30% of the second, 10% of the third, 10% of staying.
A computer that always took the best gem would be predictable. This one usually does and
sometimes does not.

Line 132 — **seven fixed standing positions**, at 20, 160, 300, 440, 580, 720 and 780. The
computer does not move to an arbitrary place; it moves to one of seven lanes. That is what
makes it readable and dodgeable. Line 133 filters out any lane with a star within 45 pixels
of it. Line 134 is the fallback: if *every* lane is unsafe, pick one edge and commit.

Line 143 — the snap. If it is within four pixels of its target it jumps exactly onto it.
That is what stops it hovering forever and jittering.

Line 144 — otherwise it moves at 300 pixels per second, capped at 1 pixel of *target*
movement per frame by the inner =clamp=.

The whole design is summarised by a single test name:
=tests/models.test.js:1252=, *"Starfall" target stability* asserts that the chosen position
does not change at all across twenty frames.

* The written records

Four markdown files at the base of the repository. None of them is documentation of the
code as it is; three of them are records of how the code got here. They are covered in
detail in *Contradictions* above, and what follows is only what a reader needs in order to
know which to trust and when.

| File | Lines | What it actually is | How current it is |
|---|---|---|---|
| =PLAN.md= | 51 | the plan for the first draft | describes a structure the code no longer has |
| =issues.md= | 461 | an audit dated 2026-09-25, then a fix pass in the same file | the audit half is stale; the last 40 lines are current |
| =REFERENCE_NOTES.md= | 28 | research notes on how the original arcade games work | deliberately records what the code *departed* from |
| =DELEGATION_LOG.md= | 55 | a record of nine separate build passes | an accurate history; its test counts are from those moments |

**=PLAN.md=** is the file the spine of this document comes from. Two of its sentences are
load-bearing for everything else:

#+begin_quote
The machine code makes decisions from current positions and collision state. It does not
skip a round, award itself points, or bypass collision checks.
#+end_quote

#+begin_quote
A static browser page cannot safely hold a Claude API key: anything sent to a browser can
be read by a visitor.
#+end_quote

The second one is why =src/ai/= talks only to the player's own machine. It is the reason the
project has no API key, no account, and no backend — and it is the reason
=issues.md= still lists *"The literal Claude requirement remains unresolved"* as a blocker.
That is not a bug in the implementation. It is a decision, recorded, with the reasoning
attached.

**=issues.md=** is the single most useful file in the repository for a reviewer, and the
easiest to misread. It contains two documents. The first, about 410 lines, is an
independent design critique with prioritized findings — and every finding in it that was
acted on is listed again in the fix pass at the end. Read the top and you will review
problems that were fixed a page later.

**=REFERENCE_NOTES.md=** is the one file that is *supposed* to disagree with the code.
Its right-hand column is headed "Our current target", and its left-hand column is what the
1980 arcade games did. It is a record of departures, not a specification. Where it says
Missile Command launches with Space, it is describing Atari's game, and the code departs
from it on purpose — which the test at =tests/models.test.js:981= confirms.

**=DELEGATION_LOG.md=** is the most honest file here, because its test counts are wrong and
that is the point — they are a record of what was true at nine separate moments. It ends:

#+begin_quote
- **Verification:** Nine tests pass, all JavaScript syntax checks pass, and a 20-run setup
  simulation shows the computer sometimes misses instead of being perfect.
#+end_quote

Today it is 77 tests. The file is not out of date; it is a changelog.

* Where the two layers end, and what this document cannot tell you

This document explains the whole codebase and it deliberately gives no opinion about it.
There are no findings here, no ranked problems, and no recommendation. The places where the
code does something surprising are described — what it does, where, and what the surrounding
code implies — and left for you.

Three things a reader should know are not covered, and cannot be from the source alone:

**The games have not been played by a person for the purposes of this document.** I ran the
77 tests and read the code. Whether Splat's race is fun, whether Breakout's special bricks
are discoverable, and whether the Starfall runner is too easy are questions the Monte Carlo
test answers only in ratio form. =issues.md= answers them from an actual play session dated
2026-09-25, and that is the better source — but it describes the code as it was then.

**The separate-browser connection has not been shown to work.** =issues.md= lists this as
blocker number one. The code is written; no human has yet confirmed a game across two
machines.

**The model download has never been exercised in this repository's own verification.**
=src/ai/on-device.js= and =src/ai/wasm-worker.js= have no test coverage, and the Imitation
test that claims to use the model stubs the model out. =REFERENCE_NOTES.md= records that
the model in use is a locally-run Llama 3.2, and =issues.md= records that this is not the
same thing as the Claude the assignment appears to ask for.

Everything else in the repository — every one of the 49 source files, every method, every
constant, every contradiction between the code and its own written record — is in this
document, quoted, with a line reference.
